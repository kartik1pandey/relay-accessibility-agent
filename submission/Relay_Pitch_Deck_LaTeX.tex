\begin{frame}{}
\eyebrowtitle{THE PROBLEM}{Point-and-click assumes hands and eyesight most people don't have}
\vspace{6pt}
{\color{inksoft}
\begin{itemize}
\setlength{\itemsep}{10pt}
\item People with limited hand mobility or low vision can't reliably operate a Windows PC through a mouse and a screen alone.
\item Existing screen readers describe a screen; they don't act on it. Existing automation agents act, but weren't built for this population's safety needs.
\item The gap: a voice-first agent that both understands the screen and acts on it --- with a person narrating every step.
\end{itemize}
}
\end{frame}

\begin{frame}{}
\eyebrowtitle{THE PRODUCT}{"Open my email and read me the new ones" --- that’s the whole interaction}
\vspace{6pt}
{\color{inksoft}
\begin{itemize}
\setlength{\itemsep}{10pt}
\item Voice in, spoken result out. No pointing, no reading required.
\item Deliberately not a general autonomous computer-use agent --- scoped assistive technology.
\item A person narrates every step, and nothing consequential happens without a spoken ``yes.'' That's a feature of the design, not a limitation.
\end{itemize}
}
\end{frame}

\begin{frame}{}
\eyebrowtitle{VERIFIED, NOT CLAIMED}{Every non-NPU piece of the pipeline has been run for real, on this machine}
\vspace{6pt}
{\color{inksoft}
\begin{itemize}
\setlength{\itemsep}{10pt}
\item Whisper speech-to-text: real transcription of a known test clip, 3 independent ways.
\item MeloTTS-EN: real synthesis, real audio, played back through real speakers.
\item The full agent.py orchestration loop: a real mic recording $\rightarrow$ real transcription $\rightarrow$ real UI Automation tree read $\rightarrow$ real guardrail gate $\rightarrow$ real action $\rightarrow$ real speech, proven end to end against a live window.
\item Chromium accessibility gap (Edge/Outlook can't be read via UI Automation): found, verified, and fixed for Edge via Chrome DevTools Protocol --- demonstrated live against a real Wikipedia page.
\item The one honest gap: LocalReasoner itself needs Snapdragon's on-device NPU (GenieX), which this dev machine doesn't have.
\end{itemize}
}

\begin{frame}{}
\eyebrowtitle{TWO SURFACES, TWO AUDIENCES}{The end user in the moment of use, and whoever configures the guardrails}
\vspace{6pt}
{\color{inksoft}
\begin{itemize}
\setlength{\itemsep}{10pt}
\item End-user runtime UI: 7 explicit states (listening, transcribing, deciding, confirming, acting, blocked, error) --- WCAG AAA contrast (7:1), verified by computed contrast ratios, not eyeballed.
\item The confirmation screen is the single highest-stakes moment in the product: distinct shape and color, never color alone, spoken aloud as well as shown.
\item Guardrail-admin surface: reads guardrails.py's real CONFIRM/BLOCK patterns directly --- can't drift out of sync with a hand-maintained copy.
\end{itemize}
}
\end{frame}
